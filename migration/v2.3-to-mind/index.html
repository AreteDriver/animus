    Migration Guide: Animus v2.3 Assistant → Animus-Mind v2.1+¶

    Date: 2026-06-30
    Scope: Port working components from the stable Assistant codebase into the Mind-class architecture
    Rationale: ADL-20260618-001 rejected the hybrid middle ground. The correct path is preserve + fork.

    Executive Summary¶

    This guide describes how to migrate from animus (Assistant-class, v2.3 stable) to animus-mind (Mind-class, v2.1+ architecture). It is not an in-place upgrade. The source repository remains frozen as v2.3-assistant-stable. The target repository is a clean scaffold that selectively copies proven components while adopting the v2.1 structural design.

    Core principle: Reuse what works. Redesign what doesn't. Archive what is dead.

    1. Repository Topology¶

    # Current (frozen)
~/projects/animus/           →  Animus v2.3 Assistant Stable

# New (active development)
~/projects/animus-mind/      →  Animus-Mind v2.1+ Mind Class

    Both are independent repositories. They do not share branches, tags, or release cycles.

    3. What Stays Behind (Do Not Copy)¶

    3.1 Dead Blockchain Packages (packages/_archive/)¶

    Action: Do not copy. Archive externally if needed.

    • animus-validator — Staking, node rewards
    • animus-prospector — Crypto opportunity hunter
    • animus-faucet — Faucet farming
    • animus-content — Write-to-earn publishing
    • animus-bounty — Task claiming
    • animus-mev — MEV extraction
    • animus-arbitrage — DEX arbitrage
    • animus-referral — Referral stacking

    Rationale: Mind-class architecture has no crypto scope. These packages are not merely unmaintained — they are out of domain.

    3.2 SQLite/JSON as Canonical Persistence¶

    Action: Do not copy LocalMemoryStore or JsonMemoryStore as canonical stores.

    Rationale: Mind architecture requires PostgreSQL as the durable authority. SQLite/JSON may exist only as rebuildable projections (search index, vector cache, graph cache). The MemoryLayer auto-selection logic (backend="auto") must be replaced with explicit canonical vs. projection distinction.

    3.3 Package-Per-Function Layout¶

    Action: Do not recreate packages/core/, packages/forge/, packages/quorum/, packages/bootstrap/.

    Rationale: The current layout has unclear ownership boundaries and version divergence (0.1, 0.8, 1.2, 1.9, 2.3). Mind architecture uses module-per-capability with a single unified release version:

    Old Package New Module Version
    animus-core (2.3.0) modules/object_core/ + modules/memory_service/ unified
    animus-forge (1.9.0) modules/agent_runtime/ + modules/trace_eval/ unified
    convergentAI (1.2.0) modules/agent_runtime/ (consciousness quorum subcomponent) unified
    animus-bootstrap (0.8.0) apps/api/ + apps/cli/ unified
    animus-kernel (0.1.0) modules/object_core/ + modules/projections/ unified
    animus-types (0.1.0) contracts/schemas/ + generated Python types unified
    animus-contracts (0.1.0) contracts/ (expanded to 22+ schemas) unified

    3.4 Imperative API Call Patterns¶

    Action: Do not copy direct function-call coupling between components.

    Rationale: Current code crosses boundaries with Python dicts and direct imports. Mind architecture uses an event bus + outbox pattern. Services consume events, not call functions. This enables: - Replay - Traceability - Idempotency - Async scaling

    4. Structural Porting Instructions¶

    4.1 Step-by-Step Port¶

    # 1. Create new repo
git init animus-mind
cd animus-mind

# 2. Scaffold v2.2 directory tree (see Section 5)
mkdir -p apps/{api,worker,cli}
mkdir -p modules/{identity_policy,object_core,source_ingestion,context_service,memory_service,agent_runtime,mcp_gateway,trace_eval,projections,recovery_governance}
mkdir -p contracts/{schemas,api,events,policies,state_machines,errors}
mkdir -p database/{migrations,constraints,seeds,verification}
mkdir -p tests/{unit,schema,contract,integration,adversarial,fault_injection,chaos,recovery,golden,end_to_end}
mkdir -p evals/{corpora,labels,queries,expected,scoring}
mkdir -p operations/{runbooks,dashboards,alerts,backup,incident_response}
mkdir -p evidence/{schemas,releases}
mkdir -p infra/{local,evaluation,shadow,limited}

# 3. Copy contracts (21 schemas)
cp ~/projects/animus/packages/contracts/*.schema.json contracts/schemas/
# Then add the 1 missing Mind schema (ledger_event.schema.json)

# 4. Copy PostgreSQL wiring
cp ~/projects/animus/packages/kernel/src/animus_kernel/memory/stores/durable.py modules/object_core/
cp -r ~/projects/animus/database/migrations/* database/migrations/
cp ~/projects/animus/scripts/setup_postgres.py scripts/

# 5. Copy eval harness
cp -r ~/projects/animus/packages/forge/eval/* evals/
cp ~/projects/animus/scripts/truth-baseline.py scripts/

# 6. Copy Bootstrap patterns
cp ~/projects/animus/packages/bootstrap/src/animus_bootstrap/dashboard/app.py apps/api/main.py
cp ~/projects/animus/packages/bootstrap/src/animus_bootstrap/dashboard/routers/conversations.py apps/api/routers/

# 7. Copy PWA shell
cp -r ~/projects/animus/packages/pwa/* apps/web/

# 8. Copy local AI stack configs
cp ~/projects/animus/packages/core/config/ai.yaml config/

# 9. Create new pyproject.toml (see Section 6)
# 10. Initialize git, add ADL-20260618-001 reference, commit

    4.2 Database Migration Path¶

    Current Animus tables → Mind tables:

    Current Table Mind Table(s) Transformation
    memories (DurableMemoryStore) object_versions + current_projections Add version column, split into ledger + projection
    tags current_projections.tags (JSONB) Inline into projection
    N/A ledger_events New — immutable append-only
    N/A outbox_entries New — transactional outbox
    N/A idempotency_records New — duplicate suppression
    N/A principals New — identity policy
    N/A capability_grants New — scope/budget/expiry
    N/A approvals New — owner approval workflow
    N/A policy_decisions New — deterministic enforcement

    Migration script required: Yes. Write a one-time loader that reads current PostgreSQL/SQLite memories and writes them as v1 objects in the new object_versions table. Mark them as imported_from_v2_3 in provenance.

    7. Risk & Mitigation¶

    Risk Likelihood Impact Mitigation
    Over-copying legacy patterns Medium High Code review every copied file against v2.2 engineering doctrine (Section 3 of roadmap)
    Under-copying working code Medium Medium Run smoke tests after each module port; if it breaks, re-copy
    Schema drift during port Medium High Schema compiler runs in CI; contract compatibility check blocks breaking changes
    PostgreSQL complexity for personal deploy Low Medium Keep Docker Compose local setup; SQLite as projection rebuild target only
    Scope creep back to general product Medium High Charter scope boundary; personal-use mandate in README
    v2.3 bug fixes needed while building Mind Low Low v2.3 is frozen; critical fixes cherry-pick to both repos

    8. Definition of Done for Migration¶

    • animus-mind repo initialized with v2.2 directory tree
    • 22 JSON schemas compile and validate
    • PostgreSQL migrations run cleanly (ledger, versions, outbox, idempotency)
    • DurableMemoryStore ported and elevated to canonical object core
    • Truth baseline passes on new repo (8/8 checks)
    • At least one end-to-end test passes (e.g., "store memory → retrieve memory")
    • Evidence bundle assembly script runs (even if empty)
    • README explains the fork: "This is Mind-class architecture. For the Assistant, see animus v2.3."
    • ADL-20260618-001 referenced in repo docs
