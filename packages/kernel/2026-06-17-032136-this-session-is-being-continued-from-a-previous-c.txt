● Ollama Explained Simply

  Ollama is a "model runner" — like Docker, but for AI models.

  # Download a model (one time)
  ollama pull qwen2.5

  # Run it interactively
  ollama run qwen2.5

  # Or hit it like an API
  curl http://localhost:11434/api/chat -d '{
    "model": "qwen2.5",
    "messages": [{"role": "user", "content": "Hello"}]
  }'

  It handles:
  - Downloading model weights (.gguf files)
  - Keeping the model in GPU memory so responses are fast
  - Conversation memory within a single session
  - Basic system prompt injection

  That's it. It does not write code, manage projects, or remember things across
  restarts.

  ---
  Qwen and Hermes

  Your friend probably means:

  - Qwen — A model family (made by Alibaba). Strong reasoning, good for coding.
  Think of it like "Llama, but made by a different lab." You'd run it as ollama 
  pull qwen2.5.
  - Hermes — Another model family (fine-tuned by Nous Research). Specifically
  tuned for "agentic" behavior — tool calling, reasoning, following multi-step
  instructions. Often better than base models at acting like a "worker" that
  uses tools.

  Both are just models you can drop into Ollama. Neither is a "system" — they're
  the brain, not the body.

  ---
  How Hermes Actually Works

  Hermes models are fine-tuned on function calling datasets. When you prompt
  them right, they output structured tool calls instead of free text:

  <tool_call>
  <name>read_file</name>
  <params>{"path": "src/auth.py"}</params>
  </tool_call>

  Or in OpenAI function format:
  {
    "function": "read_file",
    "arguments": {"path": "src/auth.py"}
  }

  The host program (Ollama, your Python script, Animus) parses that output,
  executes the tool, feeds the result back, and loops.

  This is exactly what the Animus kernel already does — just with different
  prompt formats. The SupervisorAgent + FilesystemTools loop is the same
  pattern.

  ---
  What Animus Can Learn From Hermes

  1. Prompt Discipline (System Prompt Engineering)

  Hermes is famous for not drifting. If you tell it "You are a Builder agent
  that only edits files," it stays in that lane. Current Animus prompts are
  generic. We should adopt Hermes-style role hardening:

  <system>
  You are the BUILDER agent in the Animus autonomous builder system.
  Your ONLY job is to write code edits.
  You NEVER explain. You ONLY output tool calls.
  Available tools: read_file, edit_file, run_tests
  </system>

  2. Native Function Calling Format

  Older Animus tool prompts probably use ad-hoc parsing. Hermes popularized
  strict XML/JSON function calling. The kernel should standardize on
  OpenAI-compatible function calling schema so any model fine-tuned for it
  (Hermes, Qwen, GPT-4) plugs in cleanly.

  3. Agent State Via System Prompt

  Hermes handles multi-turn agent sessions by keeping the "current mode" in the
  system prompt. Animus currently relies on Python state. Learning: put the 
  workflow stage into the system prompt on every call so the model knows if it's
  planning, building, or reviewing.

  system = f"You are in {stage.value} mode. Budget remaining:
  {budget.et_remaining}."

  4. Tool Use Discipline

  Hermes doesn't hallucinate tools as often as base models. Lesson: enforce
  strict tool schemas in the kernel's ToolRegistry so when Hermes (or any model)
  outputs a call, it validates against a Pydantic schema before execution.
